# 宁夏葡萄酒智能问答系统：数据需求与清洗规范

版本：v1.0  
编制日期：2026-11-06  
适用项目：`E:\PythonProject\NLP\QASystem`  
目标架构：Streamlit + Python + MySQL + Neo4j  
用途：指导从现有未清洗资料中抽取、核对、整理可供问答系统使用的数据。

> 本文规定目标数据的内容、格式和验收条件，不代表现有数据已经完成清洗或完成网站事实复核。保留原始数据；清洗结果另存。文中标为“演示”的记录仅解释格式，不是真实酒庄或商品资料。

## 1. 项目范围与数据目标

系统面向顾客，第一版提供五项功能：酒庄信息查询、产品基本信息介绍、葡萄酒知识问答、产品条件筛选、简单连续问答。页面采用问答窗口，数据由离线脚本维护。

MySQL 保存适合精确查询的基础事实与价格观察；Neo4j 保存实体关联、知识片段及其向量。两边通过相同业务 ID 关联。会话状态在应用中维护，不要求采集真实顾客聊天记录。

清洗后的每项信息应说明：它描述谁、具体是什么、来自哪里、适用于什么年份或规格、是否存在冲突、可以用于什么查询。

| 功能 | 必需的数据 | 合格条件 | 数据不足时的处理 |
|---|---|---|---|
| 酒庄信息查询 | 酒庄 ID、名称、位置或介绍、来源 | 可确定是哪个酒庄；具体事实有依据 | 保留已知字段，明确其余信息未收录 |
| 产品基本信息介绍 | 产品 ID、所属酒庄、名称、年份状态、规格及其他已披露参数 | 能区分酒款及记录粒度；不串用其他年份信息 | 允许部分字段为空，按已知内容介绍 |
| 葡萄酒知识问答 | 独立可理解的知识文本、主题、来源、适用对象 | 文本有信息量、语义完整、来源可追踪 | 无证据的问题保留为待补充问题 |
| 产品条件筛选 | 颜色、甜度、容量、品种、酒精度、产区及合格价格 | 参与某项筛选的字段有值、无未解决冲突，且适用粒度一致 | 缺失字段不能视为满足条件；价格不合格时不做当前价筛选 |
| 简单连续问答 | 稳定实体 ID、名称/别名、产品与酒庄关系 | 上轮结果可以被准确定位，条件可以增删或修改 | 指代不明确时澄清，不猜测对象 |

第一版不以评论情感分析、订单、支付、物流、会员、库存核验或管理员功能为数据建设目标。获奖、评分和配餐可作为扩展，缺少时不阻塞基本功能。

### 2.2 评论资料包

目录：`data_raw/宁夏数据集-王丰/`。

`reviews_all.csv` 有 2,752 条；此外存在合并前版本、平台分文件和兼容格式文件。它们可能重叠，不能简单相加为独立评论总量。

抽样内容大量涉及酒庄参观、建筑、餐饮、住宿、讲解和品酒体验。按以下规则处理：

1. 游客评论可保留为主观体验候选，不直接用来确认酒庄成立年份、产品参数、价格、营业时间或预约政策。
2. “这里的酒很好喝”没有定位具体酒款及年份，不能生成某款产品的风味或品质事实。
3. 只有明确对应具体产品、来源可追溯的品鉴描述，才评估是否进入产品描述知识；同时保留“个人评价”性质。
4. `user_name`、用户等级、IP 所在地、点赞数等不是当前五项功能的必需数据，不纳入核心清洗交付。
5. `yinchuan_winery_reviews_sentiment.csv` 的来源字段包含新闻、社区、平台等多种来源，应逐条分类，不能仅凭文件名认定全部为消费者评论或已经有情感标签。

### 2.3 需要优先解决的数据缺口

- 当前零售价及其适用酒款、年份、容量、销售单位、核验时间。
- 部分产品缺少容量、甜度、年份等筛选字段。
- 部分字段存在品种冲突或只有目录/搜索索引证据。
- 酒庄名称、公司名称、系列名、产品名之间的实体粒度和别名关系。
- 旅游评论与具体葡萄酒品鉴描述的区分。

通过清洗可以规范和筛选已有信息；缺失事实需要补采或核验。允许最终的当前零售价可用记录数为 0，并在质量报告中明确这个限制。

## 3. 清洗交付结构

建议使用以下目录。它们是数据文件与审计记录，不增加系统页面或独立服务。

```text
data_raw/                         原始文件，保持原样
data_clean/
  sources.csv                     来源登记
  wineries.csv                    酒庄主数据
  products.csv                    产品主数据
  price_observations.csv          价格观察
  entities.csv                    产区、品种、风味、知识概念
  aliases.csv                     名称与别名映射
  knowledge.jsonl                 可检索知识单元
  relations.csv                   Neo4j 关系
  audit/
    quality_issues.csv            质量问题，允许只有表头
    id_mapping.csv                合并、改号或跨包映射时必需
    field_evidence.csv            跨来源拼接字段或解决冲突时必需
    cleaning_report.md            数量、缺失、去重、冲突与功能覆盖报告
data_demo/                        如需模拟数据，单独存放
```

结构化信息以 CSV 为主，知识文本使用 JSONL。`entities.csv` 中的 Region 行可生成 MySQL 产区表；其余实体及关系导入 Neo4j。来源、别名与审计文件可由导入脚本处理，无需全部各建一个业务页面。

现有 `product_grapes.csv` 可以先作为清洗中间表保留，再生成品种实体和 `MADE_FROM` 关系；不要求重复人工维护两份品种事实。

## 4. 所有文件通用的规则

### 4.1 文件格式与空值

| 项目 | 规定 |
|---|---|
| 编码 | UTF-8；若 CSV 带 BOM，读取器使用 `utf-8-sig` 兼容 |
| 表头 | 使用本文英文名；第一行为表头 |
| CSV 转义 | 按标准 CSV 处理逗号、双引号与换行；使用解析器，不按逗号直接切字符串 |
| JSONL | 每个非空行是一条完整 JSON 对象；不加 Markdown 代码围栏 |
| 数值缺失 | CSV 空单元格；JSON 为 `null`；入库后为 NULL |
| 布尔值 | 清洗输出统一 `true`、`false`；允许未知时用空值/null |
| 数值内容 | 不夹带单位、货币符号或“左右”等文字；原始说法另存 |
| 日期 | 确知日用 `YYYY-MM-DD`；只有月份时保留 `YYYY-MM` 并标明精度，不补造某一天 |
| 多值字段 | CSV 单元格内使用 JSON 数组，如 `["S001","S002"]`；JSONL 使用原生数组 |
| 文字处理 | 清理 HTML、控制字符和无意义空白；保留否定、单位、适用条件和不确定表述 |

不能把 `未知`、`暂无`、`-`、`null` 字面字符串或目录占位 `0.00` 当成正常参数。数值 0 只在有事实意义且有证据时保留，例如明确的 0% 配比；未知配比不能填 0。

### 4.2 ID 与跨库关联

- ID 唯一、稳定，不因本次导出行号或排序变化而变化。
- 可以保留原 ID，但先检查跨文件、跨资料包是否冲突；冲突时分配新 ID，并写入 `audit/id_mapping.csv`。
- 酒庄、产品、来源、知识、实体各有独立且可区分的 ID，例如 W、P、S、K、R、G、F、C 前缀。这些前缀是项目约定。
- MySQL 与 Neo4j 中同一个酒庄或产品使用相同业务 ID。不能使用 Neo4j 内部节点 ID 替代业务 ID。
- 合并记录后，别名、价格、知识和关系中的引用同步映射；不得留下失效引用。

### 4.3 通用追溯字段

除来源表自身使用 `source_id` 外，业务记录使用以下字段；单来源的价格表仍可保留 `source_id`。

| 字段 | 要求 | 说明 |
|---|---|---|
| `source_ids` | 非空数组 | 支撑本记录的来源 ID；数组内 ID 必须在来源表存在 |
| `raw_locator` | 必填 | 可定位原始输入记录，如相对路径 + 原始 ID/行号，或 PDF 页码/网页段落 |
| `review_status` | 必填 | `accepted`、`review`、`excluded` |
| `notes` | 可空 | 限制、冲突处理、待补充信息 |

`accepted` 表示通过本轮清洗的结构与证据一致性检查，不等于重新核验了所有外部网站，也不等于信息实时有效。`review` 留在待核验区；`excluded` 留在审计记录中。正式问答数据集只读取 accepted 记录及其中允许使用的字段。

局部字段缺失或冲突不必删除整条记录。可将该字段留空、记录问题，保留其余有依据的字段。

若同一条产品记录的容量来自 S001、酒精度来自 S002，必须在 `field_evidence.csv` 中分别标明字段来源和原始定位；只写一个来源数组不足以解释字段归属。

## 5. 各类数据的字段需求

表中的“条件必填”表示：只有准备提供该字段对应功能时才必须有值；缺失不应靠推断填满。

### 5.1 来源：sources.csv

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `source_id` | 字符串 | 必填 | 来源主键 |
| `title` | 文本 | 必填 | 页面、文档或来源记录标题 |
| `publisher` | 文本 | 可空 | 发布者，不能凭链接名称猜测官方身份 |
| `url` | 文本 | 条件必填 | 网络资料保留原始链接；本地资料可空 |
| `raw_file` | 文本 | 必填 | 本次清洗读取的原始文件相对路径 |
| `source_type` | 枚举 | 必填 | `winery_official`、`region_authority`、`merchant`、`competition`、`professional_review`、`education`、`user_review`、`teaching_demo`、`other`、`unknown` |
| `evidence_form` | 枚举 | 必填 | `original_text`、`collector_summary`、`search_snippet`、`user_comment`、`unknown` |
| `published_at` | 文本日期 | 可空 | 来源发布时间，未知不补 |
| `accessed_date` | 文本日期 | 可空 | 原采集或访问时间，不用本次清洗时间覆盖 |
| `access_status_raw` | 文本 | 可空 | 原始文件登记的读取或访问状态 |
| `snapshot_path` | 文本 | 可空 | 实际存在的网页/PDF快照；没有快照时留空 |
| `dataset_role` | 枚举 | 必填 | `real` 或 `demo` |

至少保留可追踪的原始输入路径，以及可取得的 URL、原始文档名或来源定位。当前只保存摘要时，`evidence_form` 填 collector_summary；不能因采集说明写“已读网页”就填 original_text。

来源类型和可信度需要分开判断。酒庄官网适合确认自身披露，商家适合说明其特定报价，赛事资料适合确认具体奖项，游客评论适合表达个人体验；一种来源不能支撑所有类型的事实。

### 5.2 酒庄：wineries.csv

每行表示一家酒庄，不表示该酒庄的公司、门店、酒店或某一款产品。

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `winery_id` | 字符串 | 必填 | 稳定酒庄 ID |
| `name` | 文本 | 必填 | 规范酒庄名称 |
| `company_name` | 文本 | 可空 | 明确对应的运营或注册公司名称 |
| `region_id` | 字符串 | 可空 | 关联 entities 中 Region 实体 |
| `location_raw` | 文本 | 可空 | 原始位置说明 |
| `address_raw` | 文本 | 可空 | 原始地址 |
| `address_normalized` | 文本 | 可空 | 有依据的规范地址；保留修改说明 |
| `introduction` | 文本 | 条件必填 | 提供酒庄介绍时需要；简洁事实摘要 |
| `founded_year` | 整数 | 可空 | 来源明确的成立年份；区分公司成立、酒庄成立和投产 |
| `website` | 文本 | 可空 | 已确定对应酒庄的官网 |
| `telephone` | 文本 | 可空 | 保留区号，不能按数值处理 |

还需包含第 4.3 节通用字段。酒庄进入基础查询集，至少具备名称，以及有依据的位置或介绍之一。

地址整理只能处理可确认的重复、格式和错别字。不能根据名称或地图印象补造街道、门牌号、经纬度。总部、葡萄园、酒厂和游客中心地址应分清；无法确定时保留原文与说明。

### 5.3 产品：products.csv

产品记录应尽量区分酒款、系列、年份和容量。资料未披露年份或规格时，可以保留为未指定粒度的产品页记录，但不能冒充具体 SKU。

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `product_id` | 字符串 | 必填 | 稳定产品 ID |
| `winery_id` | 字符串 | 必填 | 必须引用存在的酒庄 |
| `name` | 文本 | 必填 | 保留区分酒款的名称和编号 |
| `series` | 文本 | 可空 | 系列名，不能与酒庄或单款产品混同 |
| `record_scope` | 枚举 | 必填 | `specific_variant`、`unspecified_product_page`、`catalog_candidate`、`mixed_variant` |
| `vintage` | 整数 | 可空 | 葡萄采收年份；不是获奖年、装瓶年或发布日期 |
| `vintage_status` | 枚举 | 必填 | `specified`、`non_vintage`、`unspecified`、`mixed` |
| `volume_ml` | 数值 | 可空 | 单容器容量，统一毫升；未知不默认 750 |
| `wine_type_raw` | 文本 | 可空 | 原始类型说法 |
| `color` | 枚举 | 可空 | `red`、`white`、`rose`、`other` |
| `sweetness` | 枚举 | 可空 | `dry`、`semi_dry`、`semi_sweet`、`sweet`、`other` |
| `is_sparkling` | 布尔 | 可空 | 是否起泡，未知留空 |
| `alcohol_pct_vol` | 数值 | 可空 | 14.2 表示 14.2%vol，不是 0.142 |
| `region_id` | 字符串 | 可空 | 产品明确产区；不能只据酒庄地址推定 |
| `grapes_complete` | 布尔 | 可空 | 已披露品种是否明确为完整配方；未知留空 |
| `description` | 文本 | 可空 | 对应此记录范围的客观介绍 |
| `strict_product_filter_eligible` | 布尔 | 必填 | 仅作为粗粒度资格开关，具体筛选仍检查目标字段 |

还需包含通用字段。品种与风味通过 entities 和 relations 表表达；可以另保留原始 `grapes_disclosed` 便于核对，但导入时不重复制造实体。

同名不同年份或容量不直接合并；“N.28”“珍藏”“特选”等可能区分产品的词不能当噪声删去。具体 SKU 的销售包装放在报价记录中描述。

当 `vintage_status=specified` 时，vintage 必须有值；其余状态下不填一个猜测年份。明确 NV 与未披露年份必须区分。未来年份、异常容量或异常酒精度先标记核验，不凭常识改成常见值。

### 5.4 价格观察：price_observations.csv

每行表示“某个来源在某个时间，对某个产品及销售规格给出的一条报价”。同一产品可以有多条报价。报价不是产品的永久属性。

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `price_id` | 字符串 | 必填 | 报价主键 |
| `product_id` | 字符串 | 必填 | 报价对应的产品；年份/容量不匹配时不能强行关联 |
| `amount_min` | 小数 | 必填 | 原币金额或区间下限，必须大于 0 |
| `amount_max` | 小数 | 必填 | 固定价与下限相同；区间上限不得小于下限 |
| `currency` | 字符串 | 必填 | 如 CNY、HKD，不能去掉币种后混用 |
| `unit` | 枚举 | 必填 | `bottle`、`box`、`case`、`other`、`unknown` |
| `pack_quantity` | 整数 | 条件必填 | 箱/盒含几瓶；未知不填 1 |
| `minimum_order_raw` | 文本 | 可空 | 保留原始起订条件，如“100件” |
| `price_type` | 枚举 | 必填 | `retail_observed`、`suggested_retail`、`wholesale`、`factory`、`promotion_conditional`、`reference`、`unknown` |
| `quote_date` | 文本日期 | 可空 | 来源所指报价日期，不能用观察日替代 |
| `quote_date_precision` | 枚举 | 必填 | `day`、`month`、`year`、`unknown` |
| `observed_date` | 文本日期 | 可空 | 实际采集/观察时间 |
| `verified_at` | 文本日期 | 可空 | 实际核验当前零售条件的时间，不能自动填清洗当天 |
| `tax_shipping_note` | 文本 | 可空 | 税费、运费及其他限制 |
| `source_id` | 字符串 | 必填 | 必须存在于来源表 |
| `current_retail_eligible` | 布尔 | 必填 | 有当前零售核验依据才为 true，默认 false |
| `strict_price_filter_eligible` | 布尔 | 必填 | 满足目标筛选所需比较条件才为 true，默认 false |
| `conflict` | 布尔 | 必填 | 金额、单位、年份等是否存在未解决冲突 |

还需包含 raw_locator、review_status、notes。字段资格由核验规则决定，不能仅因金额可以解析成数字就改成 true。

严格的当前价格筛选至少检查：产品及年份/容量适配、真实零售性质、CNY 或经明确规则可比较的币种、销售单位清楚、起订与促销条件匹配、核验时间及项目时效规则通过、无未解决冲突。第一版不做自动外币换算；HKD 报价保留展示资格，但不进入 CNY 预算筛选。

必须避免以下处理：

- 把批发价、出厂价、建议零售价、扫码价视为当前可购买零售价。
- 将“398元/双支礼盒”拆成 199 元后宣称顾客花 199 元即可购买；可以计算等效单瓶价，但必须保留实际购买总额与包装条件。
- 对价格区间自动取最低值，宣称准确满足“200元以内”。严格筛选应依据已确认的具体售价；区间比较只能在明确的参考模式下按既定规则进行。
- 用一条历史报价覆盖其他来源、时间或销售条件的报价。
- 将“目录显示 0.00”作为免费商品，或用均价、同系列价格补齐。

可以单独提供“历史/参考报价查询”，回答中必须带币种、性质、日期或日期不明说明。该模式与当前零售价筛选分别统计和标注。

### 5.5 辅助实体：entities.csv

每行一个规范实体，供知识关联和 Neo4j 建图使用。

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `entity_id` | 字符串 | 必填 | 全局可区分的稳定 ID |
| `entity_type` | 枚举 | 必填 | `Region`、`GrapeVariety`、`Flavor`、`Concept` |
| `name` | 文本 | 必填 | 规范名 |
| `description` | 文本 | 可空 | 有来源的简短说明 |
| `region_kind` | 枚举 | 条件必填 | Region 使用 `wine_region`、`administrative`、`unknown`，避免混淆产区与行政区 |

还需包含通用字段。Region 可以建立有依据的上级关系；不能仅凭地名相近合并。Flavor 表达有依据的描述，如“黑醋栗”“单宁柔和”，不使用模型虚构的果香强度分数。

产品类型、甜度、颜色已有结构化字段，第一版不必为每个枚举再建一个图节点。

### 5.6 名称与别名：aliases.csv

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `alias` | 文本 | 必填 | 原始称呼、中文/英文名、经核实的简称 |
| `entity_id` | 字符串 | 必填 | 对应酒庄、产品或辅助实体 |
| `entity_type` | 枚举 | 必填 | `Winery`、`Product`、`Region`、`GrapeVariety`、`Flavor`、`Concept` |
| `alias_kind` | 枚举 | 必填 | `canonical`、`abbreviation`、`english_name`、`corporate_name`、`other` |

还需包含通用字段。别名表示同一实体的不同叫法；“干红”与“赤霞珠”不是同义词，不能互设别名。同系列不同编号也不能因字面接近而合并。

公司名可以作为酒庄的检索别名，但必须有对应关系证据；不能因此把所有公司与酒庄视为同一种实体。一个别名可能对应多个实体，应保留歧义并让问答时澄清。

### 5.7 知识单元：knowledge.jsonl

每条记录表达一个相对完整的知识点，供 RAG 检索。可以是原文短摘录或忠实摘要，必须标明性质。

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `knowledge_id` | 字符串 | 必填 | 稳定知识 ID |
| `title` | 文本 | 必填 | 能说明主题，避免只写“介绍” |
| `text` | 文本 | 必填 | 可独立理解，保留对象与适用条件 |
| `category` | 枚举 | 必填 | `winery_intro`、`product_intro`、`region`、`grape`、`wine_basics`、`tasting`、`storage`、`serving`、`pairing` |
| `entity_ids` | 数组 | 必填 | 可为空数组；对应明确实体，通用知识不强绑某款产品 |
| `text_type` | 枚举 | 必填 | `excerpt`、`faithful_summary`、`subjective_opinion` |
| `fact_scope` | 文本 | 必填 | 通用、某酒庄、具体酒款/年份等适用范围 |

还需包含通用字段。source_ids、entity_ids 在 JSONL 中使用数组。

知识覆盖优先级：

1. 酒庄所在地、背景及其产品系列等已收录内容。
2. 产品的品种、类型、容量、酒精度、年份与已核实风味描述。
3. 颜色与甜度的区别、品种基础、单宁/酸度/酒体等概念。
4. 储存、开瓶后保存、饮用准备、品鉴和配餐的一般知识，保留来源中的条件。

短而完整的知识点可以直接保留。较长材料再按标题、段落切分，建议以约 200–600 个中文字符为初始观察范围，而非强制长度。不能为了达到长度拼接无关内容；不能拆掉否定词、条件或表格表头。最终 embedding 在文本清洗定稿后生成，不要求清洗人员手工填写向量。

原始 `knowledge.jsonl` 与 `rag_documents.jsonl` 中同一知识不应重复入库。产品摘要、价格摘要等派生文本由清洗后的主数据重新生成；过期报价不通过普通产品介绍片段绕过价格资格检查。

### 5.8 关联关系：relations.csv

| 字段 | 类型 | 要求 | 清洗要求 |
|---|---|---|---|
| `relation_id` | 字符串 | 必填 | 稳定关系 ID |
| `head_id` | 字符串 | 必填 | 起点业务 ID，必须存在 |
| `relation_type` | 枚举 | 必填 | 仅使用下表允许的关系 |
| `tail_id` | 字符串 | 必填 | 终点业务 ID，必须存在 |
| `proportion_pct` | 数值 | 可空 | MADE_FROM 的已披露品种配比，0–100；未知留空 |

还需包含通用字段。相同事实由多来源支持时可以合并来源数组，不重复制造同一条边；发生冲突则保留冲突记录并暂停受影响字段的使用。

| 关系类型 | 起点类型 | 终点类型 | 事实含义 |
|---|---|---|---|
| `PRODUCES` | Winery | Product | 酒庄出品产品 |
| `LOCATED_IN` | Winery | Region | 酒庄位于该区域 |
| `ORIGINATES_FROM` | Product | Region | 产品明确标注的产区 |
| `MADE_FROM` | Product | GrapeVariety | 来源明确披露使用该品种 |
| `HAS_FLAVOR` | Product | Flavor | 针对该产品记录范围的风味描述 |
| `PART_OF` | Region | Region | 有依据的区域层级 |
| `HAS_CHUNK` | Document | Chunk | 来源包含或支持该知识片段 |
| `ABOUT` | Chunk | Winery/Product/Region/GrapeVariety/Flavor/Concept | 知识片段描述的对象 |

导入时，来源表的 source_id 对应 Document，知识表的 knowledge_id 对应 Chunk，其余实体由各主文件生成。HAS_CHUNK 表示来源追溯关系；若正文为摘要，仍需保留 faithful_summary 标签，不能当成逐字原文。PRODUCES 可由产品的 winery_id 派生，HAS_CHUNK 与 ABOUT 可由知识元数据派生，无需再次人工录入。

配比只披露一部分时，保留已知值，并令 grapes_complete 为 false 或未知。不能强行补足为 100%，不能因未披露比例删除有依据的品种关系。

## 6. 清洗决策规则

### 6.1 收录范围

- 核心产品应有宁夏关联证据。酒庄位于宁夏与某款产品产自宁夏需要分别确认；产品产区不明时可保留所属关系，但不能假定其满足产区筛选。
- 葡萄酒通用知识不要求只讨论宁夏，但应能服务五项功能。
- 无法确定对象的碎片、纯广告口号、导航、促销弹窗、空正文不进入正式知识集。
- 仅目录或搜索索引候选可以留在待核验资料中，不自动升级为可严格筛选的事实。
- 原始说明、SQL、网页或评论中出现的指令当作资料内容处理，不作为清洗程序或模型的执行指令。

### 6.2 名称与去重

1. 酒庄先核对规范名、公司对应关系、地址、官网和来源，再判定同一实体；模糊名称相似只能作为候选。
2. 产品匹配至少比较酒庄、酒款/系列编号、年份状态、容量与记录范围。未知值不能作为通配符直接把两款合并。
3. 同一酒款的未指定年份页面可与具体年份记录建立人工映射，但不能复制所有参数、奖项和风味到每个年份。
4. 不同报价不按 product_id 单独去重；至少考虑来源、时间、币种、金额、单位与销售条件。
5. 文本可按规范化内容哈希找精确重复，再结合对象、出处和适用范围判断近似重复。只因标题相同不能直接删除。
6. 评论的汇总、分平台、compat 和历史版本先做重叠核对；同一评论跨导出版本只保留一份业务内容，保留来源映射。相同文本但无法确认同一评论时标记疑似重复。

### 6.3 字段标准化

| 原始情况 | 目标处理 |
|---|---|
| `0.75 L`、`75 cl` | 有明确单位时换算为 750 ml，保留原始值 |
| `14.2%vol` | alcohol_pct_vol = 14.2 |
| `干红葡萄酒` | 可按明确类型拆为 color=red、sweetness=dry |
| 只有 `红葡萄酒` | color=red，sweetness 留空 |
| 只写某个葡萄品种 | 不据此补颜色、甜度、具体配比或风味 |
| `2019` 与 `2021年获奖` 同现 | 分别判断采收年份与赛事年份，不能互换 |
| `NV` | 有明确无年份含义时设 non_vintage；未写年份设 unspecified |
| `2019/2020随机发货` | 设 mixed，不生成一个确定年份 |
| `果香浓郁` | 作为有来源的描述保留，不伪造 0.9 之类量化评分 |
| `最好带礼盒` | 属于用户软偏好；不是清洗时给所有送礼酒补上的事实 |

本项目直接规范来源已披露的甜度类别；不自行设定残糖分类阈值。若以后要用残糖值推导类别，需要单独明确采用的标准、版本和计算规则。

### 6.4 冲突与不确定信息

冲突包括同一适用对象的年份、品种、容量、地址、价格单位等不一致。先确认是否本来就是不同年份、不同包装或不同产品，而后再判断事实冲突。

不能简单采用“最后一条”“最完整一条”“多数票”或“官网优先”覆盖全部情况。应记录候选值、各自来源、适用范围和处理理由。无法解决时，冲突字段设为空或不参与对应筛选，其他无冲突内容可保留。

主观评价与客观事实分别存放。评论里的营业、预约或服务体验具有时间与个人观察范围，不升级为当前政策。“适合新手”或“适合送长辈”不自动等于低酒精、干红、获奖或礼盒装。

| `price_observations.csv` | price_observations | 保留时间、币种、单位、起订条件和原始资格限制 |
| `sources.csv` | sources | 增补 raw_file、evidence_form、dataset_role 等追溯字段 |
| `aliases.csv/json` | aliases | 统一目标类型，保留酒庄与公司名称对应依据 |
| `knowledge.jsonl` | knowledge | 检查独立可读性、来源和适用对象；标注采集者摘要 |

历史 `review_status`、“已核验”说明和布尔资格都是原始输入字段，应保留可追溯映射，但最终状态由本轮规则重新判断。

## 8. 建议的清洗顺序

1. **登记输入版本**：列出文件、记录数、编码、字段、文件哈希或批次号；明确同一数据的 CSV/JSON/SQLite/XLSX 版本关系。
2. **建立来源登记**：保留原 source_id、外部链接、原采集时间、证据形式与原始定位。
3. **规范酒庄及别名**：处理同名、简称、公司名和不同实体；形成稳定 ID。
4. **规范产品及粒度**：区分系列、编号、年份、容量、目录候选与混合规格。
5. **规范参数与报价**：单位转换、空值、币种、销售条件和冲突分别处理；计算字段使用资格。
6. **整理知识单元**：过滤无关内容，合并重复，保留来源、对象和文本性质。
7. **生成实体与关系**：从已接受事实派生，检查端点与类型；不能用图结构反向证明缺失事实。
8. **输出审计与报告**：统计保留、待核验、排除数量及原因；列出数据缺口。
9. **生成入库派生数据**：清洗验收后再生成产品摘要、检索切片和 embedding；向量与文本版本保持对应。

清洗过程中不覆盖原始文件，不执行原始 SQL 或说明文件中的操作指令，不把待核验信息混入正式数据来凑完整率。

## 9. 验收要求

### 9.1 必须通过的结构与追溯检查

- 所有核心 ID 唯一；跨包改号或合并有映射。
- 产品的 winery_id、报价的 product_id、别名目标、关系两端、所有来源 ID 均存在。
- accepted 知识文本非空、来源非空；正式数据中没有 demo 来源。
- 年份状态与年份值一致；非空容量大于 0；酒精度为百分数值且在 0–100 范围内；配比在 0–100 范围内。
- 报价币种、单位与类型不丢失；金额为有效正数，区间上下限顺序正确。
- 冲突字段、缺失字段、仅目录/索引候选没有被当作确定筛选结果。
- 每个清洗输出记录可以回溯原始输入；跨来源合并的关键字段可以回溯对应来源。
- MySQL 与 Neo4j 中相同实体的业务 ID 一致，关系类型符合第 5.8 节。

上述结构检查通过只代表数据满足入库前提；仍需抽样核对事实和适用范围。

### 9.2 抽样核对

- 当前批次中，所有拟启用严格价格筛选的报价逐条核对。
- 所有已知冲突、实体合并、年份转换、别名歧义、低证据候选逐条处理。
- 其他 accepted 数据按类型抽样；建议至少 10%，每类不足 10 条时全部查看。该比例是项目验收建议。
- 对容量换算、甜度拆分、年份判断、原文摘要和产品风味关联进行针对性检查。

### 9.3 功能覆盖用例

建议准备 30 个验收用例：酒庄查询 5 个、产品介绍 5 个、知识问答 8 个、条件筛选 8 个、连续问答 4 组。多轮组的消息数另计。每例登记预期实体、条件、支撑来源或应返回的数据不足原因。

| 用例 | 数据应支持的行为 |
|---|---|
| 某酒庄在哪里？ | 返回该酒庄已收录的位置与来源 |
| 这款酒是多少毫升、什么年份？ | 对应正确产品；未知参数如实说明 |
| 干型与颜色有什么区别？ | 检索通用知识，不把干型等同红色 |
| 找 750 ml 的干红 | 同时满足容量、颜色和甜度；未知值不混入 |
| 找 200 元以内的酒 | 默认当前价格模式下，仅使用合格报价；没有时说明缺口 |
| 找含某品种的酒 | 使用明确品种关系，不因品种常见就推断 |
| 问年份酒的奖项或风味 | 不跨年份套用扩展描述 |
| 先找干红，再说“容量改成375毫升” | 更新容量，保留仍有效的类型条件 |
| 问“第二款是哪家酒庄的？” | 使用上轮有序产品 ID 查询所属酒庄 |
| 同名/简称对应多个对象 | 保留歧义并澄清 |

验收问题不作为知识事实自动回填。问答模板、人工预期答案和实际资料证据分别保存，避免用生成答案证明其自身正确。

### 9.4 清洗报告必须包含

1. 每类原始、去重、accepted、review、excluded 记录数；说明记录或分片的计数口径。
2. 每个核心字段的非空数量、冲突数量、可参与对应筛选的数量。
3. 价格按币种、类型、日期精度、单位和筛选资格的分布。
4. 来源按实际证据形式的分布，及无法追溯原始来源的数量。
5. 去重、实体合并、ID 映射、未解决问题与待补采清单。
6. 五项功能各自可覆盖的范围，特别说明价格筛选和具体年份产品描述的限制。
7. 清洗版本、执行日期、规则版本；派生摘要与 embedding 的对应版本由后续入库流程登记。

## 10. 格式示例与审计字段

以下是结构演示，使用虚构数据和 DEMO 来源，不能进入正式事实集。

### 10.1 一个演示知识单元

```json
{"knowledge_id":"K_DEMO_001","title":"演示酒庄A的位置说明","text":"演示资料将演示酒庄A的位置记为某地；此句仅用于说明数据格式。","category":"winery_intro","entity_ids":["W_DEMO_001"],"text_type":"faithful_summary","fact_scope":"演示酒庄A","source_ids":["S_DEMO_001"],"raw_locator":"data_demo/example.txt#段落1","review_status":"accepted","notes":"演示记录；对应来源 dataset_role=demo，只放 data_demo。"}
```

### 10.2 审计文件字段

| 文件 | 建议字段 | 触发条件 |
|---|---|---|
| `quality_issues.csv` | issue_id、record_type、record_id、field、issue_type、raw_value、handling、source_ids、status | 全批次输出，零问题时可只有表头 |
| `id_mapping.csv` | input_file、original_type、original_id、clean_type、clean_id、action、reason | 改号、合并或跨包映射时必填 |
| `field_evidence.csv` | record_type、record_id、field、raw_value、clean_value、source_id、raw_locator、evidence_kind、decision | 跨来源字段拼接、冲突处理、关键单位/年份转换时必填 |

常见 issue_type 可使用 missing、conflict、ambiguous_entity、duplicate_candidate、invalid_unit、unclear_vintage、untraceable_source、reference_price_only、out_of_scope。采用枚举便于统计，发现问题不等于自动排除整条记录。

## 11. 第一版实施优先级

| 优先级 | 交付重点 | 完成标志 |
|---|---|---|
| P0 | 稳定酒庄/产品 ID、所属关系、来源、基础参数、核心知识 | 可以有据地查询已知信息并识别缺失 |
| P1 | 规范品种/产区/风味关系、别名、筛选字段资格 | 可完成有数据支撑的组合条件筛选和指代查询 |
| P1 | 当前价格的补采与核验 | 得到真正合格的当前报价；若仍没有则明确不支持该子功能 |
| P2 | 具体年份的专业评价、奖项、配餐描述 | 作为附加解释，不混入无证据的基础字段 |
| P2 | 旅游体验或主观评论 | 经筛选后作为附加资料，保留主观性质 |

先做一小批贯通验证，再按同一规则扩展。验收依据是来源、粒度、字段可用性和功能覆盖，而非把所有字段填满。

## 12. 交付前检查清单

- [ ] 原始文件保持不变，清洗结果另存。
- [ ] CSV/JSON/SQLite/XLSX 多种载体没有被重复统计成新增资料。
- [ ] 名称、别名、公司名、系列、产品已分清。
- [ ] 同名不同年份/容量没有混并，NV 与未披露年份已区分。
- [ ] 缺失容量没有默认 750 ml，未知参数没有补常见值。
- [ ] 颜色与甜度分开，品种未被用来臆测配方或口味。
- [ ] 所有报价保留币种、性质、时间、单位和销售条件。
- [ ] 当前价格资格经过实际核验；历史/批发/索引报价没有冒充当前单瓶价。
- [ ] 未解决冲突已登记，受影响字段不参加严格筛选。
- [ ] 旅游评论、专业评价、供应商描述与客观事实已区分。
- [ ] 每条正式知识有来源、适用对象和文本性质，摘要不伪装成原文引述。
- [ ] 主数据与派生 RAG 文本已去重，旧价格不会从文本旁路进入回答。
- [ ] 所有关系端点与来源引用有效，MySQL/Neo4j 业务 ID 一致。
- [ ] 演示数据与正式数据分开。
- [ ] 输出了质量报告、功能覆盖情况和待补采清单。
