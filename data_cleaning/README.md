# 数据清洗说明

适用项目：宁夏葡萄酒智能问答系统。规则版本：1.0.0。

## 1. 目录与交付

本文件夹与项目根目录的 `data_raw`、`data` 同级。全部清洗代码集中在本文件夹；业务结果、待核验记录、辅助评论与审计结果都写入 `data`。

```text
QASystem/
  data_raw/                  原始资料，不修改
  data_cleaning/
    clean.py                 清洗主程序
    rules.json               当前资料包的人工核对规则、名称保护与风味词表
    validate.py              输出验证与文件完整性验证
    test_clean.py            关键边界情况回归测试
    README.md                本说明
  data/
    *.jsonl                  可供正式问答加载的主数据
    review/                  待核验主记录
    excluded/                排除记录
    auxiliary/               辅助待审评论与其来源
    audit/                   清洗决策与追溯
    schema.json              业务记录JSON Schema
    quality_report.json      数量、完整性与覆盖范围
    manifest.json            输入/输出文件哈希、规则和代码版本
    validation_report.json   验证结果
    README.md                数据结构、枚举与使用说明
```

本次遵循项目的数据需求与清洗规范，并按用户最新要求将原先建议的 CSV 交付改为 JSON/JSONL，输出目录改为 `data`。Markdown 仅用于说明文档。没有创建额外数据库服务或管理员页面。

## 2. 运行方法

只使用 Python 标准库，建议 Python 3.11 或更新版本。无需安装 pandas、数据库服务器、模型或第三方清洗库。

在项目根目录执行：

```powershell
python data_cleaning/clean.py --as-of-date 2026-11-06
python data_cleaning/validate.py
python -m unittest discover -s data_cleaning -p test_clean.py -v
```

`--as-of-date` 是判断未来年份的评估日，不会被写成来源发布时间、报价日或当前价核验日。省略时使用中国时区当天日期。

需要不同路径时：

```powershell
python data_cleaning/clean.py --raw-dir data_raw --output-dir data --as-of-date 2026-11-06
```

输出不能等于、位于或包含原始数据目录。程序不执行原始 SQL、说明文件或文本中的指令，不联网，不调用大模型，不生成 embedding。后续向量化应基于已验收的正式知识文本另行实施。

主程序会直接运行输出验证；验证失败会返回非零退出码并在 `data/validation_report.json` 中保存原因。修正规则后可重跑。程序仅覆盖自己管理的同名输出，不递归删除目录或额外用户文件。

## 3. 输入选择与版本核对

程序自动寻找同时含 `products.json`、`wineries.json` 的唯一结构化资料包，存在多个包时停止，避免任意选择版本。

- 酒庄、产品、来源、报价、专业评价、别名、品种关系和原始质量问题以包内 JSON 为主载体。
- 对同名 CSV 逐字段核对，处理数字、布尔、数组与空值的载体差异；不一致时停止。
- 只读打开 SQLite，核对对应表记录数，不执行原始查询脚本，不写入数据库。
- 基础知识读取 `knowledge.jsonl`。旧 `rag_documents.jsonl` 只登记派生记录，不重复导入；检索文本由清洗后主记录重建。
- XLSX、检查输出、同内容的导出副本和来源事实登记文件登记到输入清单，不叠加为新的业务记录。
- 评论包读取 CSV 与携程 JSONL；通过身份和文本规则合并可确认的重复，不以所有文件行数相加作为独立评论数量。

运行前后核对全部原始文件的 SHA256。后续运行 `validate.py` 也会与 manifest 中的原始输入哈希比较。原始资料确实新增或更新后，应重新运行清洗，以生成新的输入清单。

## 4. 主数据处理流程

### 4.1 来源与证据

来源保留 URL、标题、原采集日期、原访问状态和实际证据形式。本批以采集者摘要为主；没有网页原件时 `snapshot_path=null`，不会把“事实核对说明”标为网页快照。

登记记录 accepted 只表示可用于追溯。能否支持某条产品或知识事实，仍检查资料取得方式。只有索引、目录候选或正文未取得的记录放入 `review`。

### 4.2 酒庄、年份与产品范围

- 保留原业务 ID，同一酒庄、产品在 MySQL 和 Neo4j 使用同一个业务键。
- 酒庄、公司、产品系列和单款产品分别处理，不按名称相似度自动合并。
- 指定年份、明确 NV、年份未披露、混合年份分别表示；无年份数字且 is_non_vintage=false 仍是“未披露”，不会自动当作 NV。
- 不从获奖年、基酒年、装瓶年补产品年份，不把未指定年份网页参数复制给其他年份。
- 容量未知保持 null；明确的 L/cl 才换算为 ml。酒精度保留百分数值。
- 颜色与甜度分开，只根据明确披露或“干红/干白”等明确类型词规范；不根据葡萄品种猜颜色。

当前包中的具体处理在 `rules.json` 登记：

| 对象 | 处理 |
|---|---|
| W009 亿众酒庄 | 2018是公司成立年，转存 company_founded_year；酒庄 founded_year=null |
| P003 玉鸽宋彩干白 | 品种正文与图片标签冲突；正式品种数组为空，候选关系留在review |
| P034 芬享半甜桃红 | 甜度冲突留空，同时保持索引候选状态 |
| P043 Bloom Brut | 保留含米酒的配方说明，停用普通葡萄酒筛选资格 |
| P014 西鸽X黑比诺 | 目录可见但详情不可用，不能因目录来源已读而进入正式数据 |

人工规则带 expected_names 保护。原 ID 对应了其他名称时程序停止，避免把旧规则错误套到新数据上。新增或更换资料包后应复核并更新规则版本。

### 4.3 字段级筛选资格

每条产品保存 `field_filter_eligibility` 与 `field_filter_reasons`。例如产品可以用于750ml查询，但年份缺失时不用于年份筛选。品种冲突不影响其无冲突的容量或酒精度字段。

原始的总筛选布尔标志仅作为追溯字段，不直接继承。目录候选、弱来源和不确定父酒庄会保守隔离；因此部分来源明确的产品也可能因酒庄主档只有索引证据而暂留review。

同一记录含多个来源却没有字段级明确归因时，不随意指定其中一个。审计标为 `record_level_candidates`，相关精确筛选字段保守停用。品种关系若有独立明确的来源，可单独保留资格。

### 4.4 报价

所有报价作为独立观察保留，原币金额、币种、报价性质、销售单位、起订条件和日期不混并。参考报价分为正式可追溯参考记录与待核验记录，后者位于review。

本次未联网核验零售条件，因此 33 条报价的 `current_retail_eligible`、`strict_price_filter_eligible` 始终为 false；产品 `price_cny` 始终为 null。HKD 不自动折算 CNY，历史建议价、出厂价、扫码价不升级为当前零售价，观察日不替代报价日。

### 4.5 知识与图关系

- 通用知识保留条件、否定和来源，不根据项目常识补写不存在的百科内容。
- 基础产品参数片段和酒庄基本信息按规范主记录重建，修正年份范围、成立年与冲突字段旁路问题。
- 产品品鉴描述明确保留来源评价性质；只关联对应具体产品和年份，不传播到同系列。
- 风味词表仅在来源已出现的描述中做字面抽取，处理局部否定和长短词覆盖，不给风味虚构强度分数。
- 品种、产区、风味和知识主题生成稳定哈希 ID；关系两端都需要存在。
- HAS_CHUNK、ABOUT、PRODUCES 等可由规范字段派生；不猜测行政区或产区的上下级关系。
- 原知识、产品摘要、专业描述的数量分别统计；派生摘要不是新增独立网页证据。

## 5. 评论处理与去重边界

评论只输出到辅助待审区，不生成客观产品参数或当前预约/营业政策。未绑定到确切产品的“好喝”“果香”等描述不进入产品风味图。

1. 统一不同表头、HTML、转义换行、Unicode空白和日期格式；相对日期、缺少年份的日期不补造。
2. 明确移除姓名、用户等级、IP位置等用户档案字段；正文对手机号、邮箱、证件号及IP做规则脱敏。不能据此宣称所有个人信息均已识别。
3. 同平台外部评论 ID 且规范正文相同，可以合并；已确认的 `ctrip_数字ID` 与携程原始数字ID统一，原值仍保留。汇总前后版本相同采集 ID 且正文相同，可以合并。
4. compat兼容导出只有一个满足平台、对象与日期兼容条件的文本副本时，合并并保留全部输入位置。
5. 单纯相同文本但身份不明确时，保留记录并标记疑似重复；相同 ID 不同正文保留变体并登记冲突。
6. 源石、龙谕等不在已接受酒庄主档中的标签保留原文，winery_id=null；不会据游客文件名创建已核实酒庄主档。
7. 新闻、社区等来源不因放在评论文件内而认定为真实消费者评论；来源不明文本标为 unclassified_excerpt。

评论来源表在 `data/auxiliary/review_sources.jsonl`。所有合并记录均保留 `original_records` 和 `raw_locators`，可以解释原始行数如何变成清洗后数量。

## 6. 验证与复跑

`validate.py` 检查：

- 每个业务 JSONL 的结构、类型、枚举与状态目录一致性。
- ID唯一、来源引用、产品归属、别名目标、图关系端点与节点类型。
- 正式记录不能引用待核验产品或实体；正式知识不能只有搜索索引证据。
- 年份状态、空值、数值范围、字段筛选资格和参考报价限制。
- 产品知识不含旧报价金额，评论不会作为产品事实使用。
- 高风险样本 P002/P003/P014/P043/P055/W009 的回归规则。
- 评论行数守恒、来源与显式个人资料字段移除。
- 原始文件和输出数据的 SHA256 完整性。

`test_clean.py` 覆盖单位转换、未知值、NV与基酒年、混合/未来年份、日期精度、否定风味、脱敏、类型和目录候选等边界。

同一原始输入、同一代码/规则和同一 `--as-of-date` 会得到相同的业务与审计输出。manifest记录代码哈希；修改代码后应重跑。manifest与validation_report不纳入自身输出哈希，避免自引用。

## 7. 本批结果与使用限制

最新精确数量以 `data/quality_report.json` 和 `data/README.md` 为准。首次完成批次的主要结果为：22家正式酒庄、47条正式产品、138条正式知识；33条报价均保留为参考或待核验，当前零售价筛选可用数为0。

9,725行评论输入包含多个导出载体；确认重复合并后为3,137条，其中3,135条辅助待审、2条低信息量排除。不能将它们称为3,137位独立消费者或3,137条已验证购买评价。

清洗完成的是可追溯的本地数据整理，不是外部真实性认证。继续开发时，先读取根目录 accepted 数据；review、excluded、auxiliary用于质量复核，不与正式RAG混合加载。需要当前价格、完整SKU或尚未覆盖的知识主题时，依据质量报告补采资料，再重新运行清洗。
